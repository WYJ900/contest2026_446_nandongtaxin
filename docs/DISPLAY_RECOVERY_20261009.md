# 2026-10-09 复位黑屏排查与恢复

## 现场证据

关闭 EPIC 后，用户最初确认显示和触摸正常，但第一次复位再次黑屏。直接通过 LCD
驱动输出红绿蓝色带也不可见。因此“CPU 绘制解决了黑屏”这一早期判断已撤回。

诊断版本在同一台设备上读回如下值，所有寄存器读取的 HAL 返回值均为 0：

| 寄存器 | 正常显示 | 复位后黑屏 |
| --- | --- | --- |
| 芯片 ID（04h） | 331100h | 331100h |
| 电源/显示状态（0Ah） | 9Ch | 0Ch |
| 像素格式（0Ch） | 55h | 77h |
| 亮度（52h） | 7Fh | 00h |
| 显示控制（54h） | 20h | 28h |

黑屏启动的早期日志仍读到 9Ch/55h，随后变成 0Ch/77h。说明初始化之后面板配置
发生丢失；软件缓存的 `power=100` 和 DMA 完成均不能证明实际屏幕正常。
具体是谁或哪一电气事件触发了配置丢失，目前尚未确定，不能归因于 EPIC。

同一固件不重烧、不复位主控，仅执行 `velaride lcd-recover` 后寄存器恢复；用户确认
表盘和触摸恢复。后续读回也保持 9Ch/55h/7Fh。这是恢复路径的真机证据。

## 修改

- UI 线程每秒在帧间检查实际唤醒状态和 RGB565 格式；仅在屏幕期望开启且检测到状态
  丢失时执行恢复。先等待在途传输结束，再重新初始化面板并请求完整重绘。
- 恢复成功后再次读回状态；失败返回错误。诊断输出记录恢复次数。
- 屏幕供电操作仅切换面板自身 VADD 和复位脚，保留共用 VSYS/3V3，避免重置其他设备。
- `lcd-wake` 也排队到 UI 线程执行，避免串口线程与异步送屏同时操作控制器。
- 面板初始化的毫秒等待改用可恢复的系统睡眠。诊断实测旧 20ms 空循环为
  20,014–20,043us，未证明旧延时不足；不将此项单独描述为黑屏根因修复。
- CPU 绘制继续保留；这不是 EPIC 被证明有问题的结论。

`lcd-diagnose` 读回面板状态，`lcd-recover` 在 UI 线程执行独立屏幕恢复。
本项目新增的 LCD ioctl 需要随 NuttX、板级驱动和应用补丁一起使用。

## 验证边界

加入检查与恢复的中间版本完成两次复位，寄存器保持正常，用户确认滑动、触摸、
运动菜单及中文复盘正常。原第 7 条骑行记录和 AI 原文保持完整，无重新上传。

最终收窄共用供电、加入恢复计数并移除临时延时测量的版本，已完成独立恢复与一次复位。
复位后寄存器为 9Ch/55h/7Fh，累计送屏 118 次、完成 118 次，恢复计数为 0；原 AI
正文读回完整。用户随后反馈时间不对，并确认网页已重新连接。网页完成 `ping`、
`time_sync` 和 `ride_latest` 确认；18:29:45 串口读回与电脑时间一致，屏幕状态仍为
9Ch/55h/7Fh，送屏 508 次、完成 508 次，恢复计数为 0。

BLE 辅助脚本先遇到 Windows 特征发现失败，随后扫描超时，已保留失败记录，不能
计为通过；最终成功证据来自用户重新选择设备后的网页。最终版全部界面的逐项视觉
确认不应与前述中间版用户确认混为一谈；最终反馈明确指出的是时间问题，已完成校时。

当前无有效 RTC 时间时只恢复上次保存的校时值，不能推算断电期间的经过时间；
网页每次连接成功会自动校时。此次并未修改 RTC 驱动或声称解决离线断电走时。
不能把短时测试等同于长期稳定性，也不能将硬件状态恢复机制称为已定位全部触发原因。

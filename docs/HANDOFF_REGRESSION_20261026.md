## 2. 用户的目标与约束

用户最初希望在已有手表上增加可听、可说的语音能力，通过手机中转离开电脑使用。后来明确调整顺序：

1. 先恢复旧的全部功能，包括高帧率滑动、触摸、抬腕、菜单、设置和骑行交互。
2. 在完整基础功能上单独加入麦克风，证明没有破坏基础功能。
3. 再增加新蓝牙／手机 App 联动；云端语音识别、模型、合成后接。

原版已经有供网页使用的 BLE 数据服务。“再加蓝牙”指新增手机联动，不是删掉原有 BLE。

用户不接受“亮了但不能滑”的降级交付，不希望每次新增功能都损坏已验收功能，也不希望喇叭持续播放。相关要求已写入工作区及团队仓 `AGENTS.md`。当前没有持续放音，也没有进行录音。

## 6. 故障时控制链与诊断局限

### 原版为什么会黑屏

1. 板级异步初始化 LCD，然后调用 FT6146 初始化。
2. FT6146 复位后，通过 I2C 读取 `0xa3`、`0x9f`。读取失败会返回错误，撤销触摸节点注册。
3. 原表盘程序等待 `/dev/lcd0` 和 `/dev/input0`；触摸缺失则超时退出。
4. 系统和 BLE 可能仍在运行，但表盘任务没有运行；因此不能把 BLE 成功当作显示正常。

典型失败输出：`ls /dev/input0` 失败；`wake-status` 的 `off=0, sleeps=0, idle=4294967295ms`，`nav-stats` 帧数为 0。一次正常自动熄屏则能看到有效输入设备、活动计数和 `off=1/sleeps>0`。两种状态应分清。

### 已有总线对照

| 状态 | 软件读取结果 | 解释边界 |
| --- | --- | --- |
| 主板单独上电，屏幕断开 | SCL=1、SDA=1；地址阶段 NACK | 无屏幕时 NACK 正常 |
| 只接排线到主板，屏幕端悬空 | SCL=1、SDA=1；地址阶段 NACK | 该状态没有观察到持续拉低，不能排除弯折／插接后的间歇问题 |
| 屏幕接上且故障时 | SCL=0、SDA=1，起始阶段等待超时 | 没有开始有效地址传输，不能把它写成“读到了错误芯片 ID” |
| 先 GPIO 释放总线、复位低 20 ms | SCL=0、SDA=1 | 尚未证明复位电平实际到达屏幕芯片 |
| 再释放复位并等 200 ms | SCL=0、SDA=1 | 仍失败；不能直接推出芯片损坏 |
| 屏幕端完全拔下再接后，曾多次恢复 | `/dev/input0` 存在，用户能滑动和抬腕 | 连接状态、屏幕断电／上电顺序等变量同时改变，尚未分离 |

`touch_probe` 不在开机时执行；设备已注册、总线活跃或开机未满 20 秒时拒绝运行。它把 PA37/PA33 切为 GPIO 输入释放，用拉低／释放的方式模拟 I2C，不主动推高总线，测试结束恢复保存的引脚配置。**这不是纯只读命令**：它还实际复位触摸芯片；恢复保存的引脚寄存器不等于外设内部状态也完全回到测试前。

这些是 **GPIO/HAL 软件读数，不是示波器或万用表测量**。没有实测屏幕电源、电阻、复位脚波形；采样时的 FSEL/DOER 配置也没有用外部仪器交叉验证。因此不能认定具体短路点、触摸 IC 损坏或整块主板损坏。

读取到的关键寄存器：I2C1 `BMR=0x01`（SDA 高、SCL 低），I2C2 对照 `BMR=0x03`。引脚路由曾为 `I2C1_PINR=0x2125`（SCL 37、SDA 33）。功放 PA42 当时为输入下拉、读值低，只能说明**检测当时**没有持续高电平使能，不能排除上电瞬态。

`i2c get` 打印 `Transfer failed: 1` 是工具层将失败返回值取反显示，不能当成明确的底层 NACK 编码。HAL 复位会清除部分错误状态；仍需在第一次错误发生时捕获原始 HAL ErrorCode／控制器状态。

## 8. 音频和 App 工作保留到什么程度

- v13 接受的输出是特定 `musicusb` 固定片段、USB 供电、8Ω/1W、软件峰值限制后的结果；配置和原始声音参数见 [扬声器记录](SPEAKER_TEST_20261020.md)。不是任意音频都可直接加 6 dB 的保证。
- v14/v15 麦克风：16 kHz、16-bit、单声道；ADC0 DMA request 39；最长 5 秒；v15 起丢弃启动前 200 ms。数据经偏移、长度和 FNV-1a 校验后导出 WAV。
- v16 已知录音上传 153,600 字节，读回一致，板端回放约 4.8 秒，用户听清。原始人声留在本机 `exports/voice/`，不放入本次交接包。
- 后来的独立麦克风候选仅录音／导出和锁文件，**录音一次都未执行，就在前置触摸检查中失败**。不要把 v14 的人声验收套用到这个候选。
- 安卓 APK：`exports/mobile/VelaRide-0.1.0-debug.apk`，原生 Android API 26+、目标 35，开发签名。实现连接、校时、骑行缓存、前台 GPS、备注回传；无网络和手机麦克风权限。没有实际安卓设备联调，也没有蓝牙音频传输或 AI 对话。
- 原版 rc17 的旧 BLE 不支持新 App 所用的 `phone_clear` 等扩展。当前以恢复基础为主，新 App 与原版协议不完全匹配是已知状态，不要误诊为旧 BLE 硬件损坏。

## 10. 复现入口与操作注意点

以下路径相对 `D:\desktop\VelaRide_AI`。先只读状态；不要为了阅读交接而直接重复刷机。

```powershell
# 只读：无 --reset。显式 UTF-8，避免把输出编码错误误认为板子故障。
py -3 -X utf8 tools/serial_probe.py --port COM5 `
  --command 'uptime' --command 'ls /dev/input0' `
  --command 'velaride wake-status' --command 'velaride nav-stats' `
  --wait 1 --log backup/restore-20261026/next-readonly-check.log
```

控制台可能被 `ai_agent` 占用，提示符为 `vela>`；稳定启动后发一次 Ctrl-D 可回到 NSH。不要盲目连发或把 `Unknown command` 当成命令不存在。首次冷启动期间输入可能落在不同控制台，日志应记录原始响应。

串口脚本在打开前设置 DTR/RTS 为 false，未主动使用 reset；但这不等于已经用仪器证明开／关串口时线路绝无变化。工程历史曾记录串口连接与复位／黑屏耦合，需要把“持续保持一个串口连接”与“反复打开关闭”分别对照。`SFBL` 出现后不宜继续把 NSH 命令当作有效应用操作。

特别注意：每次 `serial_probe.py` 结束都会关闭串口。“后面没有再发送命令”不等于关闭后的 RTS/DTR 电平已证明无影响。应优先在不周期发送命令的情况下保持一个连接，观察应用，再独立对照关闭连接；不要同时改固件、重插排线或更换供电。这个因素目前未被实测排除，也未被证实为根因。

当前原样 rc17 不含 `touch_probe`。该命令只存在于特定诊断镜像；不要把它当成当前固件的可用命令，也不要不核对版本就执行诊断步骤。

如确需原样回退，用户已授权恢复的应用镜像范围是：

```powershell
.\sftool.exe -q -c SF32LB52 -p COM5 -b 1000000 `
  --before default_reset --after soft_reset --connect-attempts 2 `
  write_flash --verify `
  'my-contest-repo/artifacts/rc17-baseline-20261026/firmware.bin@0x12010000'
```

静默模式成功日志可能为空；必须同时记录进程退出码、使用的文件哈希和后续状态。一次 U7 写入曾报 `timeout while waiting for RAM command response`，后来重试成功；不能假定失败发生在写入前或镜像完整。不要全片擦除，不要覆盖 `0x129a0000` 起的配置区。

## 11. 建议接手后的排查顺序

1. 先核对本文最终状态、固件完整 SHA-256 和当前控制台。保留一份实际现场状态，不先修改 UI 或继续加音频。
2. 在固定接线、供电和 USB 端口条件下，区分 MCU 软件复位、完全断电、屏幕端完全断开再接三种操作；每轮只改变一个变量，记录 `/dev/input0`、界面任务、复位原因和首个错误。
3. 用一次持续串口采集尽量覆盖“正常运行 → 静置黑屏 → SFBL”的全过程，并单独评估串口打开／关闭、DTR/RTS 的影响。用户最后明确说没有先碰线或按键。
4. 捕获 I2C 第一次失败前后的 HAL ErrorCode／状态寄存器，注意 `HAL_I2C_Reset` 会清错误。确认 MCU 实际引脚模式、电平与屏幕侧复位／电源，而非仅看软件输出锁存值。
5. 若有万用表、示波器或同规格备用排线，检查屏幕端供电、复位是否到达、SCL/SDA 在断电及不同连接条件下的状态。没有这些测量前，不认定具体元件损坏。
6. 补做“原样 rc17 → 纯重建 rc17（无麦克风）→ 同一父代仅加麦克风”的严格对照。当前遗漏了中间重建镜像的单独实机验收。
7. 如确认是底层初始化／复位问题，只修已证明相关的最小范围；处理重复注册、失败清理与有效重试。不能再用删掉触摸依赖、只显示表盘来冒充原交互恢复。
8. 基础功能在多次冷／热启动和静置后均通过，再冻结新基线。然后麦克风、最后新蓝牙／App，每阶段均复查触摸、滑动、抬腕、帧率、原记录和已验收功能。

## 12. 已纠正的说法与过程问题

- “加麦克风后屏幕就坏了”不能作为已定位因果；候选失败发生在录音未执行时，而且旧镜像、同一旧镜像运行中也出现异常。
- “恢复了”曾只覆盖当次交互，没有验证反复启动／静置稳定性，过早进入下一阶段。
- v19 亮屏但缺少触摸，是降级状态，不是原功能恢复。
- 一次所谓“串口断开”实际是 Python stdout 的 GBK 编码异常，COM5 仍在线；已改用 `-X utf8`。另有真正 COM5 不存在的时段，两者不能混写成同一种故障。
- 旧代码并非完全丢失：已找到原 U7 构建树、阶段备份和 rc17 还原方法；但重建 rc17 未做完整二进制等价证明。
- 本轮在新功能过程中修改过共享启动／触摸初始化，又缺少统一验收和完整版本对应，这是过程问题。即便最终根因含硬件因素，也不能据此忽略回归管理问题。

## 3. 黑屏问题必须保留的结论

1. 最初关闭 EPIC 后能显示，但复位仍黑屏，直接色带也不可见；“关闭 EPIC 就修好”已被否定。
2. 正常/黑屏实际读回分别为：电源状态 `9C/0C`，像素格式 `55/77`，亮度 `7F/00`；芯片 ID 都是 `331100`。软件 `power=100` 和 DMA 成功不足以证明显示正常。
3. 不重烧、不重启整机，仅独立重初始化屏幕后恢复，已由用户确认。具体导致面板配置丢失的代码路径或电气事件仍未定位。
4. 当前 UI 线程在帧间每秒检查真实状态，异常时等待在途传输结束、恢复屏幕并完整重绘。恢复后再次验证状态并累计次数；保留共用 VSYS/3V3，避免影响其他设备。
5. `lcd-wake` 排队到 UI 线程，避免与送屏并发。面板等待改用系统睡眠；旧 20ms 延时实测约 20ms，不能声称“延时不足是根因”。

**验证版本不要混淆：**

- 加入检查与恢复的中间版：两次复位后，用户明确确认画面、滑动、触摸、运动菜单、复盘均正常。
- 最终基线：独立恢复与一次复位后，寄存器正常；最后采样送屏 508 次、完成 508 次、重启后恢复计数 0。用户指出时间不对，随后已通过网页校准并串口核对。最终版完整逐项视觉检查不应冒用中间版的确认。
- 自动检测后的恢复分支仍需受控故障复现验证；独立恢复命令通过，不等于覆盖所有自动恢复场景。

## 6. 接续操作

先进行不会改变设备状态的检查（Windows 工作区根目录）：

```powershell
git -C .\my-contest-repo status --short
Get-FileHash .\my-contest-repo\artifacts\velaride-huangshan-pi-20261009.bin -Algorithm SHA256
& .\my-contest-repo\scripts\apply-integration.ps1 -Check
node .\my-contest-repo\scripts\sync-web-gateway.mjs --check
```

日常网关：在 `my-contest-repo/web-gateway/` 运行 `npm test` 和 `.\start-ai.ps1`。若改 Web 主源，先运行 `node my-contest-repo/scripts/sync-web-gateway.mjs --apply` 更新本机镜像，再确认启动的是哪一个目录的服务。

固件构建：先将本次修改的明确文件同步到 WSL，再运行：

```powershell
wsl -d Ubuntu-22.04 bash /mnt/d/desktop/VelaRide_AI/tools/wsl_build.sh
```

改配置时核对板级 defconfig、活动 `.config` 和生成 `include/nuttx/config.h`；不能只改 Windows defconfig 就认为镜像生效。曾发现未重新生成头文件导致 EPIC 实际仍开启，必须核对生成配置与链接符号。
`tools/wsl_sync.sh` 会删除并重建 WSL 工作树，**不是日常增量同步命令**；不得为接续工作直接运行它。

只有需要安装新固件时才执行 `.\tools\flash.ps1 -Port COM5`。该脚本取的是 **WSL 当前输出**，不是团队仓归档固件；回退时必须明确选择已校验的归档镜像，不能直接运行脚本就声称回退。不要擦除配置分区。

需要诊断时，下面的命令不主动复位，但仍会占用串口：

```powershell
py -3.13 -X utf8 .\tools\serial_probe.py --command "velaride lcd-diagnose" --command "velaride ride-latest" --command "velaride review-read" --log .\display-readback.log
```

发生黑屏先保留现场，再按证据考虑 `velaride lcd-recover`。`--reset` 是显式整机复位，`lcd-test` 会切到色带；两者不能混入无说明的日常读数检查。不要使用 `persist-format`、测试记录写入或整片擦除来验证保留已有用户记录。

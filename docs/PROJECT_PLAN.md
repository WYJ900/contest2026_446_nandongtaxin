# VelaRide AI 骑行安全腕上助手

> 本文件保留开发阶段的原始规划。当前完成度、稳定演示路径和已知限制以仓库根目录
> `README.md`、`docs/VALIDATION.md` 和 `docs/KNOWN_LIMITATIONS.md` 为准。

## 1. 项目概述

### 1.1 项目名称

VelaRide AI 骑行安全腕上助手

### 1.2 一句话定位

面向城市骑行者，利用黄山派的腕上屏幕、触摸、运动传感器和蓝牙能力，结合 openvela AI Agent，为用户提供出发前行程规划、骑行中状态与安全提醒、异常情况主动提示以及骑行结束后的 AI 复盘，减少骑行过程中频繁查看手机带来的安全风险。

### 1.3 目标用户

- 城市通勤骑行者
- 周末休闲骑行者
- 短途电动车/自行车用户
- 希望记录和改善骑行习惯的用户

### 1.4 要解决的问题

1. 骑行时频繁拿出手机查看路线和状态，存在安全风险。
2. 用户容易忘记休息，长时间连续骑行后疲劳程度不可见。
3. 普通骑行记录工具大多只记录数据，不能主动提醒和执行操作。
4. 骑行结束后缺少简洁、可执行的复盘建议。

## 2. 目标平台

### 2.1 目标开发板

立创黄山派（SF32LB52）。

### 2.2 选板理由

黄山派已经完成 openvela 适配，官方板级配置已经启用快应用、蓝牙、LCD、触摸、LVGL、RTC、PWM、ADC、NOR Flash 以及 LSM6DSL 六轴运动传感器，适合作为低功耗可穿戴设备原型。

板载能力可以覆盖本项目的核心需求：

- AMOLED 屏幕：显示骑行状态、提醒和 AI 复盘；
- FT6146 电容触摸：完成滑动、确认、暂停和结束等操作；
- 实体按键：骑行中进行盲操作；
- LSM6DSL：检测运动、停止、冲击和姿态变化；
- RTC/硬件定时器：统计骑行时间并触发主动提醒；
- BLE：与 iPhone 交换骑行状态和 AI 结果；
- NOR Flash：断线或离线时保存骑行记录；
- PWM：使用 RGB LED 对提醒等级进行提示；
- USB-UART：固件烧录、日志采集和问题定位。

项目初期不需要额外购买摄像头、麦克风、Wi-Fi 模块或外接显示器。iPhone 作为网络、GPS 和 AI 服务网关，不计入新增硬件采购。

## 3. 功能规划

### 3.1 AI 出发规划

用户在 iPhone 端输入目的地、预计出发时间和骑行时长，AI 生成简短的出发建议，包括预计时间、休息安排和注意事项，并同步到黄山派。

所需能力：BLE、LCD、触摸、NOR Flash；iPhone 提供 GPS 和网络。

### 3.2 骑行状态腕上显示

黄山派显示当前骑行时间、运动状态、手机同步的速度/距离信息、下一条提醒和连接状态，减少用户查看手机的次数。

所需能力：LCD、触摸、BLE、RTC、LSM6DSL。

### 3.3 主动安全提醒

AI Agent 根据连续运动时间、运动状态、手机同步数据和异常事件主动提醒：

- 连续骑行时间过长，建议休息；
- 长时间静止，询问用户是否需要结束或暂停；
- 检测到明显冲击后持续静止，提示用户确认安全；
- 手机连接断开或电量不足时提醒用户。

所需能力：LSM6DSL、RTC、硬件定时器、LCD、BLE、PWM、NOR Flash。

### 3.4 腕上操作执行

用户可以通过触摸或按键执行“开始骑行、暂停、继续、记录事件、结束骑行、发送预计到达时间”等操作。

所需能力：触摸、实体按键、LCD、BLE、RTC。

### 3.5 骑行记录与断线补传

设备本地保存开始时间、结束时间、运动时长、暂停次数、异常事件和用户操作。手机或网络暂时不可用时仍可完成核心记录，重新连接后自动补传。

所需能力：NOR Flash、RTC、BLE、USB CDC。

### 3.6 骑行结束 AI 复盘

AI 根据骑行时长、运动状态、休息次数、异常事件和用户标记生成复盘，包括：

- 本次骑行概况；
- 连续运动是否过长；
- 休息安排是否合理；
- 异常事件摘要；
- 下一次骑行建议。

复盘结果通过 BLE 返回黄山派，在腕上屏幕上以卡片形式展示。

所需能力：NOR Flash、BLE、LCD；云端使用 Xiaomi MiMo Token Plan。

## 4. 技术方案

### 4.1 总体架构

```text
黄山派 openvela
  ├── 快应用界面
  ├── ai_agent / @system.velaclaw
  ├── LSM6DSL 运动检测
  ├── RTC / Timer 主动提醒
  ├── LCD / Touch / Button / PWM
  ├── NOR Flash 本地记录
  └── BLE GATT 通信
          │
          ▼
iPhone 网关应用
  ├── CoreBluetooth
  ├── CoreLocation
  ├── 骑行状态采集
  ├── HTTPS 网络转发
  └── AI 结果回传
          │
          ▼
自建服务端 + Xiaomi MiMo
  ├── 骑行数据接收
  ├── AI 出发建议
  ├── AI 异常摘要
  └── 骑行结束复盘
```

### 4.2 设备端

代码基于 openvela 大赛分支：

```text
dev-ai-contest-2026
```

设备端采用 openvela 快应用框架和 AI Agent：

- 快应用：实现页面、卡片、计时、状态操作和结果展示；
- QuickJS/VelaJS：执行应用逻辑；
- LVGL/openvela 图形能力：渲染黄山派屏幕界面；
- LSM6DSL：读取加速度和角速度；
- RTC/Timer：实现连续骑行计时和定时主动提醒；
- NOR Flash：保存本地记录和断线缓存；
- BLE GATT：传输骑行数据和 AI 结果；
- PWM：输出不同级别的 LED 提示。

### 4.3 AI Agent 和自定义 Skill

开发一个名为 `ride-safety` 的自定义 Skill，放置在：

```text
/data/agent/skills/ride-safety.md
```

Skill 负责：

- 识别“开始骑行”“暂停骑行”“结束骑行”等意图；
- 读取 RTC、运动状态和本地记录；
- 判断是否达到主动提醒条件；
- 写入骑行事件；
- 触发快应用提醒界面；
- 调用云端 AI 生成出发建议和骑行复盘。

项目必须展示一个完整的“主动 + 执行”场景：

> 用户开始骑行后，Agent 持续读取运动状态和骑行时长；连续运动达到阈值时主动提醒休息；用户点击“休息”后，Agent 修改骑行状态并记录事件；骑行结束后，Agent 读取本次记录并生成复盘。

快应用通过以下方式调用端侧 Agent：

```javascript
import velaclaw from '@system.velaclaw'

const result = await velaclaw.ask({
  query: '根据本次骑行记录生成简短复盘'
})
```

### 4.4 Web 网关（当前最小演示方案）

为加快参赛闭环，第一阶段不开发完整 iPhone App，使用桌面 Chrome/Edge 的
Web Bluetooth 连接黄山派。网页负责：

- 连接 `FFF0/FFF1/FFF2` GATT 服务；
- 连接后自动下发 Unix 时间；
- 模拟手机 GPS 的速度和距离；
- 读取手表骑行状态；
- 请求服务端生成 AI 复盘并回传手表。

网页同时提供不依赖 BLE 的演示模式，用于先验收页面、接口和复盘流程。iPhone
Safari 当前不支持 Web Bluetooth；若最终必须在 iPhone 上直连，再增加一个只负责
CoreBluetooth 收发的薄原生壳，继续复用相同 JSON 协议和服务端。

实现目录：

```text
web-gateway/
```

详细协议见 `project-docs/WEB_GATEWAY_BLE_PROTOCOL.md`。

### 4.5 iPhone 应用（后续增强）

iPhone 端使用原生 Swift 开发，主要承担网关职责：

- `CoreBluetooth`：连接黄山派并读写 GATT 特征；
- `CoreLocation`：获取 GPS、速度和位置变化；
- `URLSession`：将数据发送到自建服务端；
- 本地缓存：网络不可用时暂存数据；
- BLE 回传：将 AI 结果和提醒配置传回设备。

第一版只实现一个简单 BLE 服务，使用 JSON 数据传输，不实现复杂地图导航。

### 4.6 服务端和 AI

最小演示版服务端先只提供：

```text
POST /api/ride/review
GET  /api/health
```

`start/events/finish` 暂由设备本地状态与 NOR Flash 承担，后续产品化再拆分接口。

服务端负责接收骑行数据、调用 Xiaomi MiMo Token Plan，并返回：

- 出发建议；
- 主动提醒内容；
- 异常事件摘要；
- 骑行结束复盘。

设备端保留确定性逻辑，例如计时、阈值判断、本地存储和离线提醒；云端只负责自然语言理解和总结，避免项目变成纯云端应用。

## 6. 最终演示流程

1. 用户在黄山派上点击“开始骑行”；
2. iPhone 通过 BLE 接收设备状态，并提供 GPS/速度数据；
3. 黄山派显示骑行时间和当前运动状态；
4. 连续运动达到阈值后，AI Agent 主动提醒休息；
5. 用户点击“休息”，设备记录事件并更新状态；
6. 模拟一次异常静止或冲击事件，设备主动发出安全确认提醒；
7. 用户点击“结束骑行”；
8. 服务端调用 Xiaomi MiMo 生成骑行复盘；
9. 复盘结果通过 BLE 返回并显示在黄山派屏幕上。

## 7. 风险与降级方案

- 如果 iPhone GPS 或后台 BLE 受系统限制，先使用前台运行和模拟数据完成演示；
- 如果云端 AI 暂时不可用，使用设备端固定规则完成主动提醒，并保留本地记录；
- 如果真实 LSM6DSL 数据调试延迟，先使用模拟运动数据验证完整流程；
- 如果黄山派暂时无法运行完整 AI Agent，先在 openvela 模拟器完成 AI 流程，再将快应用和硬件能力逐步迁移到真机。
